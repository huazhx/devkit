# Operations API specification (v1, 2026-10-21)

The web page, the CLI and the service's internal scheduled jobs change data only through the **standard operations** listed in this file. Each operation touches only the card, fields or inbox entry it names; no operation can upload the whole board. The rules (state changes, the event ledger, plan timestamps, migration) exist in one copy only, in the server's Python.

Why: before 2026-10, clients uploaded the whole `board.json` and relied on `savedAt` for CAS and a three-way merge. A tab left open for a long time, holding a valid token and stale content, could overwrite the whole board and wipe out cards an agent had just created (the "Use mine, overwrite external changes" button). The merge base lived in the browser's local storage, shared by all tabs, and could also misread "I don't have this card" as "I deleted it". The operations API rules out this whole class of problems by construction: deletion can only be an explicit operation and is never inferred from absence.

## 1. Storage

`BOARD_DATA_DIR/board.sqlite` (SQLite, from the Python standard library). `journal_mode=DELETE`, `synchronous=FULL`: the backup process opens the same file read-only, and a WAL-mode database cannot be opened on a read-only mount.

| Table | Columns | Notes |
|---|---|---|
| `meta` | `key TEXT PRIMARY KEY, value TEXT` | `rev` (global revision number, integer), `saved_at` (time of the latest change, in milliseconds), `last_active_id`, `board_version` (=2) |
| `cards` | `id TEXT PRIMARY KEY, ord INTEGER, rev INTEGER, body TEXT` | `body` is the whole card as JSON (including `events`; empty fields are not stored), `rev` is this card's revision number, `ord` keeps the array order from the import; a new card takes the maximum + 1 |
| `inbox` | `id TEXT PRIMARY KEY, ts INTEGER, body TEXT` | `body` is `{id, ts, text}` |
| `ops` | `seq INTEGER PRIMARY KEY AUTOINCREMENT, op_id TEXT UNIQUE, ts INTEGER, actor TEXT, client_id TEXT, op TEXT, args TEXT, undo TEXT, response TEXT` | Operation log, append-only. `undo` stores the old values of the changed fields, or the full text of a deleted object, for manual recovery |

The schema version is kept in `PRAGMA user_version`. Changing the schema = appending a function to the end of the migration list in `board_store.py`; at startup, migrations that have not run yet are executed in order, one transaction per migration.

## 2. Read

`GET /board.json` returns:

```json
{ "version": 2, "rev": 1234, "savedAt": 1760000000000, "lastActiveId": "…",
  "threads": [ <card view> ], "inbox": [ {"id": "…", "ts": 0, "text": "…"} ] }
```

**Card view** = the stored card + `"rev"` (this card's revision number) + `"derived"`:

```json
"derived": { "breakpointAt": ms|null, "nextActionAt": ms|null, "enteredAt": ms|null,
             "doneAt": ms|null, "trashedAt": ms|null, "restoreTo": "ready"|…,
             "sessions": [ {"ts": ms, "out": ms, "capped": bool, "noticedAt"?: ms} ] }
```

`derived` is computed by the server from `events` according to `board_schema.py`; it is not stored, and clients do not send it back. `threads` is sorted by `ord`; `inbox` by `ts`, descending.

`GET /api/ops?limit=N&before=SEQ` returns the recent operation log (`seq` descending; 50 entries by default, at most 500).

## 3. Write

`POST /api/ops`, request body:

```json
{ "api": 1, "opId": "<uuid generated by the client>", "op": "<operation name>", "args": { … } }
```

Headers: authentication (session cookie or `Authorization: Bearer`), and `X-Client-Id` (used over SSE to tell a client's own changes apart).

| Status | Body | Meaning |
|---|---|---|
| 200 | `{"ok": true, "rev": N, "opSeq": S, "changed": {…}, "result": {…}, "duplicate": bool}` | Executed (or this `opId` was already executed earlier: `duplicate: true`, and it is not executed again) |
| 400 | `{"error": "bad_request", "detail": "…"}` | Unknown operation, or missing or invalid arguments |
| 400 | `{"error": "api_version", "detail": "…"}` | Unrecognized `api` version (client and server do not match; the CLI first updates itself automatically and then reruns, see ARCHITECTURE §6) |
| 404 | `{"error": "not_found", "detail": "…"}` | The named card or inbox entry does not exist |
| 409 | `{"error": "stale", "detail": "…", "card": <card view>}` | A field in `if` has been changed elsewhere; nothing was written |
| 409 | `{"error": "op_id_reused", "detail": "…"}` | The same `opId` came with a different operation or different arguments |
| 422 | `{"error": "rule", "detail": "…"}` | An invariant would be violated (a second running card, permanently deleting a card that is not in the Trash, an unconfirmed import, etc.); nothing was written |

`changed`: `{"cards": [card view…], "removed": [id…], "inbox": [all entries] (present only when the inbox changed), "lastActiveId": "…" (present only when it changed)}`. The client replaces / appends / removes by id and does not recompute any rules.

An operation that changes nothing (for example, the value is unchanged) returns 200 with an empty `changed.cards` and an unchanged `rev`; it is still recorded in the operation log so that it stays idempotent.

Every successful operation that changes something does the following in one transaction: update the affected rows, `rev + 1` on each changed card, `meta.rev + 1`, `saved_at = max(now, old value + 1)`, and write one `ops` row; after the commit, SSE broadcasts `{"type": "change", "rev": N, "origin": "<X-Client-Id>"}`.

**`if` condition**: `card.update`, `card.switch` and `plan.step` may carry `"if": {field: expected old value}`. Before comparing, missing, `null` and `""` are treated as the same value; for `plan`, only `tracks` is compared (canonical JSON). Any field that differs → 409 stale. Only the fields the caller intends to change need to go into `if`; someone else changing other fields of the card is not a conflict.

**`touchedAt`**: every operation that changes a card sets it to the time of that operation (except `card.purge`).

Old endpoints: `PUT /board.json` and `POST /merge` return 410 `{"error": "gone", "detail": "writes now go through POST /api/ops; reload the page or update the CLI"}`. Old pages that are still open can therefore no longer overwrite the whole board. `POST /notify` remains (broadcast only).

## 4. Operation list

The time `now` is taken once by the server at the start of the operation and shared by all events within that operation.

| Operation | Arguments | Effect and rules |
|---|---|---|
| `card.create` | `title` (required), `priority`=1, `lane`="project", `due`, `deliverable`, `log`, `blockingOthers`, `cadence`, `nextAction`, `breakpoint`, `state`="ready"\|"blocked", `waitingOn`, `plan` | The server generates `id` (uuid4), `createdAt`=`touchedAt`=now, `events`=[]. When `nextAction` / `breakpoint` is non-empty, one event is recorded for each; when `state`="blocked", one state event is recorded and `waitingOn` is written; the `plan`'s `summaryAt`=now. `result: {"id": …}` |
| `card.update` | `id`, `set: {field: new value}`, `if` (optional) | Changeable: `title` (non-empty), `priority` (0/1/2), `due` ("" or YYYY-MM-DD), `deliverable`, `breakpoint`, `nextAction`, `waitingOn`, `blockingOthers`, `lane` (project/standing/errand), `cadence` (positive integer or null), `log`, `plan` (null = delete; otherwise an object whose `tracks` is an array, each element with `kind` flow or q; every step of a flow must have a non-empty `t` of at most 30 characters, and may have a boolean `done` and a string `detail`), `sample` (can only be set to null; used to clear an old marker). `breakpoint` / `nextAction` go through `set_text` (an event is recorded only when the value changes). `plan`: if `tracks` changed, `summaryAt`=now; if not, the old `summaryAt` is kept; a `summaryAt` given by the client is ignored. `state` is not changed here |
| `card.state` | `id`, `to` (ready/running/blocked/done/trashed), `waitingOn` (optional) | Same state = no change. Entering running: another card already running → 422. Leaving running: `lastActiveId`=this card. Entering ready or running: delete `waitingOn`. Entering blocked: write `waitingOn` if it is given |
| `card.restore` | `id` | Must be in the Trash (otherwise 422). Target state = `derived.restoreTo` (the state before entering the Trash; ready if that state was running; ready if there is no record); the rest is the same as `card.state` |
| `card.reenter` | `id`, `nextAction` (non-empty) | Re-entry after "Stale breakpoint": `set_text(nextAction)`, then enter running under the `card.state` rules |
| `card.switch` | `from` (the current running card), `to` (the target card; may be empty = pause only), `breakpoint`, `nextAction`, `dest` (ready/blocked), `waitingOn`, `startTarget`=true, `if` (on `from`'s breakpoint / nextAction) | One transaction: `from` must be running (otherwise 422); `set_text(breakpoint, reaffirm=True)` (an event is recorded even if the value is left unchanged, meaning it was reconfirmed), `set_text(nextAction)`, `from` enters `dest`, `waitingOn` is written when `dest`=blocked and deleted otherwise, `lastActiveId`=`from`; when `to` is non-empty and `startTarget` is set, `to` enters running and its `waitingOn` is deleted. When the target's breakpoint is already stale, the web page passes `startTarget: false` and then sends a separate `card.reenter` |
| `card.purge` | `id` | Must be trashed (otherwise 422). Deletes this row; `undo` stores the whole card |
| `note.add` | `id`, `text` (non-empty) | Appends `{ts: now, kind: "note", text}` |
| `note.delete` | `id`, `ts`, `text` | Deletes the event with `kind=note` whose `ts` and `text` are both equal (the first one found searching from the end); not found → 404. `undo` stores the deleted entry |
| `inbox.add` | `text` (non-empty) | New entry `{id: uuid4, ts: now, text}`. `result: {"id": …}` |
| `inbox.delete` | `id` | Deletes it; an entry that no longer exists = no change (no error). `undo` stores the entry |
| `inbox.promote` | `id` | Promotes the entry to a new card: `title`=the first 40 characters of text, `state`=ready, `priority`=2, `lane`=project, `nextAction`=text (records one na event); deletes the entry. Not found → 404. `result: {"id": new card id}` |
| `inbox.move` | `id`, `card` | Appends the entry's text to `card` as a note and deletes the entry. Either one not found → 404 |
| `plan.step` | `id`, `track` (an index into `plan.tracks`, or a flow track name: exact match first, then substring; must be unique), `step` (0-based index), `done` (bool), `if: {"text": the text of this step}` (optional) | Sets this step's `done`; `plan.summaryAt`=now. Step text does not match → 409 stale |
| `plan.q` | `id`, `n` (position among the q tracks, 1-based), `decide` (string or null), `today` (YYYY-MM-DD) | `decide` non-empty: `status`=decided, `answer`, `at`=today; null: `status`=open, delete `answer` and `at`. `plan.summaryAt`=now |
| `board.import` | `board` (a whole v2 or v1 board), `confirm`=true | Only for the web page's "Import and overwrite" and for maintenance. Not confirmed → 422. First exports the current data to `BOARD_DATA_DIR/pre-import-<ms>.json.gz`, then replaces everything; `undo` records only that file name and the counts |

Internal service operation (not over HTTP, `actor`="server"): `board.sweep`, which moves a card that has been RUNNING for more than 6 hours back to ready automatically; same rules as `sweep()` before the redesign.

## 5. Client conventions

- Every response to a request authenticated with an API token carries `X-Board-Client: <version>`, which is the content hash of the client package the server ships with its image. `GET /api/client` (authentication required) returns `{"version": "…", "files": {"relative path": "text content", …}}`. These two are the only channel through which old clients find a new version: fields may only be added, and nothing may be broken (ARCHITECTURE §6).

- Generate a new `opId` for every operation. On a network error, retry once with the **same** `opId`; the server deduplicates by `opId`, so a retry never records a note twice.
- The web page does no optimistic updates and keeps no local copy of the data: send the operation → wait for the response → update the in-memory view from `changed` → redraw. When it receives someone else's change over SSE, it fetches `GET /board.json` again. When the server cannot be reached, the page is read-only and says that this operation was not saved.
- 409 stale: re-read, tell the user "This card was just changed elsewhere", and let the user redo it; do not retry automatically.
- The CLI's red line (breakpoint / next action need `--user-verbatim`) and "do not create a duplicate card with the same name" are usage rules for AI and stay in the CLI; data rules exist only on the server.

## 6. Migration and rollback

- `board-admin.py import-json <board.json>`: imports an existing `board.json` into a **new** `board.sqlite` (refuses if one already exists, unless `--replace` is given, in which case the old database is exported before it is replaced). After the import it automatically exports once and compares card by card with the original file (ignoring `savedAt` and `rev`); on any mismatch it deletes the new database and reports an error.
- `board-admin.py export-json [--out FILE]`: exports the whole board in its stored shape (without `derived`). Both backup and rollback use it.
- If at startup there is only a `board.json` and no `board.sqlite`, the service refuses to start and asks you to run `import-json` first; it does not migrate automatically.
- Rolling back to the old version: stop the new service → `export-json --out board.json` → start the old image.
